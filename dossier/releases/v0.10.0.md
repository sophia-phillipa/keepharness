# 0.10.0 — Mediated Jira publication and evidence-based recovery

## Behavior and acceptance

Codex and Claude native/scoped executions receive a harness-owned, execution-scoped
MCP server (named `harness_effects` in isolated/strict configuration; native Codex
uses a fresh `harness_effects_<random>` name to avoid host-table merging). Its only tool, `prepare`, validates and stores
an immutable Jira create-issue artifact and request, creates a P1 publish gate and
returns the request ID immediately. The human wait lives in the harness, outside
the MCP call and provider timeout. Both plain chat and standalone invocations use
this path. Workflow orchestration is deferred to P4.

The gate shows operation, Jira endpoint, project destination, arguments, artifact
preview and both digests. Approval requires the existing P0 enrolled human session
and job owner. API tokens, MCP capabilities, localhost access, `full` and Claude
`bypassPermissions` cannot approve. Decisions are single-use and are never
remembered. The harness revalidates the operation, destination, arguments digest,
artifact digest and current integration contract immediately before dispatch.
Changed requests, artifacts or contracts invalidate approval.

The provider can finish while a publication awaits its human. The durable gate
remains in Needs you, its chat card and Pipeline. Restart explicitly invalidates
pending gates and prepared requests, requiring a new request. A dispatch interrupted
before its receipt checkpoint becomes `unknown`, never a queued retry.

Effects persist intent before network dispatch with a correlation key. The Jira
Cloud REST v3 driver implements only `POST /rest/api/3/issue`, adding the label
`harness-effect-<key>` without changing the approved stored artifact. It stores the
returned issue key. Labels are correlation evidence, not Jira-side deduplication.
Update, transition and every other integration remain advisory.

Pipeline and span detail project effect intent, approval identity, execution,
binding digests and external receipt from events through `events_to_spans`; there
is no spans table. Artifact content follows the existing content opt-in for spans;
the human gate displays the artifact needed to make the decision. Text is rendered
with text nodes. Replayed events and a completed provider turn do not close a
still-pending publication gate.

An enrolled owner can choose **Reconcile → Check evidence** or **Keep unknown**.
Checking uses Jira's enhanced `POST /rest/api/3/search/jql`, validates the exact
marker and project, and accepts only unambiguous evidence. Empty or ambiguous
searches remain `unknown`; repeated checks have persisted exponential backoff.
The action records the human decision and never publishes again. There is no
button or API to force an unknown result to success without evidence.

## Integration contract and credentials

The owner adds a nonsecret contract to the harness runtime configuration. For
example (reserved example domain; this is not a real destination):

```json
{
  "effect_integrations": [{
    "integration": "jira-team",
    "operation": "jira.create_issue",
    "endpoint": "https://jira.example.invalid",
    "destination_allowlist": ["DEMO"],
    "mediated": true,
    "credential_binding": "jira-team"
  }]
}
```

Provision its binding from an owner terminal:

```sh
python -m agent_service.integrations --config /path/to/runtime.json --binding jira-team
```

The command prompts for the account email and reads the API token without echo.
Neither is passed in command arguments or provider environments. The separate
harness-owned store defaults to `state_dir/harness.effect_credentials.json`, with
0600 permissions and no-follow reads; `effect_credentials_path` can select another
private path. There is no HTTP/MCP credential write endpoint. The store must remain
outside all worker mounts. Configured bindings, credentials and remote response
bodies are not copied to prompts, events or stderr. This is minimal owner-side
provisioning, not the P5 vault. Control-panel configuration editing is not added.

A prepare request is a JSON object containing `integration`,
`operation: "jira.create_issue"`, `destination` (an allowlisted project key),
`arguments: {}` and `artifact: {"fields": {...}}`. Fields must include that exact
project key, a nonempty summary and an issue type; Jira validates any additional
field requirements. The harness reserves its correlation-label prefix. Contracts
use HTTPS; loopback HTTP is accepted for synthetic protocol fixtures. The driver
does not follow redirects or inherit proxy configuration.

## Transport and enforcement limits

| Mode | Prepare transport | Publication label |
| --- | --- | --- |
| Codex native / Claude native | Per-process stdio MCP with a temporary socket capability | `unenforced`: same-user filesystem access is not an isolation boundary |
| Codex scoped / Claude scoped | Per-execution MCP inside the existing bubblewrap workspace; only the prepare socket is mounted | `mediated` only when actual mounts and copied authentication cannot expose harness stores; otherwise `unenforced` |
| Gemini / DeepSeek / local and unsupported modes | No effect executor registration | `unenforced`; unsupported transport is recorded |

The short-lived Unix socket accepts only `prepare` for its bound execution. It
cannot resolve gates or dispatch effects. Its capability expires when the adapter
returns; already prepared effects retain their separate human gate. The reserved
MCP name cannot be supplied through selected host configuration. No personal MCP
configuration is edited. Other native shell/environment publication paths remain
unenforced; project access defaults are unchanged.

0600 alone cannot hide data from an unrestricted process running as the same OS
user. Native modes therefore make no containment claim. Scoped checks compare the
actual venv mount, project/additional roots, session directory, copied auth file,
CLI/code host and system binds with the private stores. These checks do not replace
trusted owner configuration or provide a general-purpose credential vault.

## Migration and HTTP contracts

The additive `effects` schema persists immutable request/artifact bindings,
approving identity, correlation key, outcome/receipt and reconciliation backoff.
Existing jobs, ownership, project defaults, `sem-projeto` and Tailscale identifiers
remain unchanged. An old database upgrades through the existing migration path.

- `GET /v1/jobs/{job}/effects`: authenticated job-owner inspection, no-store.
- Existing `POST /v1/approvals/{gate}`: enrolled human resolution with
  `{"choice":"approve"}` or `{"choice":"deny"}`.
- `POST /v1/effects/{effect}/reconcile`: enrolled owner decision, either
  `{"decision":"check"}` or `{"decision":"keep_unknown"}`, no-store.

The Jira protocol references are Atlassian's official
[create issue](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/#api-rest-api-3-issue-post)
and [enhanced issue search](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/#api-rest-api-3-search-jql-post).
No live Jira or real credentials were used for validation.

## Security self-review

Authors and reviewers were distinct for executor/credentials, transport and UI.
Before the final suites, review and regression tests addressed:

- Request operation/destination mutation could be masked by stored approval fields
  during projection. Request values now remain distinct from the immutable binding
  and mutations are rejected before intent or dispatch.
- A host MCP named `harness_effects` could impersonate the reserved executor.
  Real installed CLI tests proved that Codex deep-merges override tables: replacing
  a table did not remove inherited HTTP fields. Native Codex now uses an
  unpredictable execution name and disables reserved host entries from the actual
  `CODEX_HOME` without changing their transports. This also avoids an invalid
  transport-less disabled entry. Scoped instructions explicitly permit prepare
  while leaving publication to the harness.
- Venv executable symlinks made isolation checks inspect a different directory
  from the actual bind. Checks now use the actual runtime directory and include
  copied auth, code-host and system binds.
- A valid prepare response exceeded the default 64 KiB stream limit, leaving a
  persisted gate behind an apparent tool failure. The bounded response reader now
  accepts the maximum stored request plus its preview; a large-response regression
  proves the complete round trip.
- Incomplete socket clients delayed capability shutdown. Execution teardown now
  cancels clients before waiting for server closure and closes their streams.
- A late approval HTTP response could overwrite an invalidated gate in the UI.
  Terminal SSE state now wins. Provider completion no longer infers an end for
  a durable pending publish gate/effect.

## Simulated profile matrix

| Profile | Main and recovery checks |
| --- | --- |
| P1 beginner | Read operation/destination/artifact evidence; denial leaves a clear terminal decision |
| P2 rushed user | Repeated approval submits once; late response preserves invalidation |
| P3 domain professional | Replay preserves artifact/digest; malformed HTML stays literal text |
| P4 keyboard user | Approve/Deny reachable by keyboard; terminal decision restores focus |
| P5 mobile/reconnection | Narrow layout; replayed resolved gate stays disabled |
| P6 harness engineer | Enrollment denial/recovery; request binding and receipt provenance |
| P7 UI/UX reviewer | Unknown outcome, Reconcile guidance, human decision and continued unknown status |

These are synthetic scenarios, not research with real users or screen-reader
certification. Tests never contact real Jira, use real credentials or opt into
provider inference. No systemd, push, merge or remote repository action occurred.
JEV was unavailable because tool approval is required under the environment's
`never` policy; local contract/risk prioritization was used without bypassing it.
The Maestro pilot remains closed; token/cost metrics are unavailable.
