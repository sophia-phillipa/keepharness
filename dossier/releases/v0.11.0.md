# Version 0.11.0 — Declarative workflows and general Maestro

## Behavior and acceptance

Workflows are bounded sequential declarations with one to twelve terminating
invocations. The slash palette lists project `workflows/` and explicitly trusted
catalog workflows. Existing plan cards, gate cards and the Run console are reused;
this release changes no CSS or layout. Conversational agents remain standalone.
Parallel, repeat and nested workflows are rejected.

JSON is always supported. YAML is optional and uses `yaml.safe_load` only when
PyYAML is already installed; the package adds no mandatory dependency. Without
PyYAML, select JSON. Documents and expanded values are bounded; ambiguous or
unsupported declarations fail closed.

A minimal project file, `workflows/review.json`:

```json
{
  "version": 1,
  "id": "review",
  "steps": [
    {
      "id": "inspect",
      "kind": "builtin",
      "resource_id": "builtin/roles/reviewer",
      "args": "Review the supplied evidence and cite sources.",
      "backend": "local",
      "model": "installed-model",
      "effort": "configured"
    }
  ]
}
```

Model identifiers must exist in the installation. Resource steps use the canonical
invocation's `kind`, `resource_id`, verbatim `args`, `mode` and optional
`requested_backend`; backend/model/effort follow current project candidates.
The legacy planner fields `role/backend/model/effort/task/reason` remain accepted.
Additional step fields are `gate`, `publish`, `requires`, `inputs`, `outputs` and
`condition`. Schema fields are `type`, `properties`, `required`, `items`, `enum`
and `description`, with bounded nesting. Requirements can name permissions,
integrations, operations and execution mode and are checked against available
capabilities.

A condition is exactly `{ "from": "inspect.ready", "is": true }` (or `equals`).
It reads one fenced `harness-result` JSON object of at most 16 KiB from a prior
step's answer. Missing, malformed or ambiguous results request a gate. A true
condition continues; a false one skips the step. When `outputs` declares a schema, invalid structured output also
requires explicit review. Conditions cannot grant publication authority.

A `publish` step remains labelled unenforced unless the P3 effect transport
establishes mediation. An `effect` object requires `publish: true` and carries the existing prepare request
(`integration`, `operation`, `destination`, `arguments`, `artifact`). The supported
operation remains `jira.create_issue`, with a configured integration and destination
allowlist. The executor
persists preparation, waits for a single-use human gate, checks immutable bindings
and records execution/receipt. Auto planning never approves effects.

## Coordinator and planning policy

Set `maestro_coordinator` to `{ "backend": "local", "model": "installed-model" }`
(optionally `effort`) in owner-managed control settings or runtime configuration.
Any enabled, eligible backend can coordinate. Codex remains the default; an
explicit unavailable coordinator fails instead of silently switching providers.
The historical Codex error remains accepted for default-coordinator failures.

The planner prompt is packaged as `agent_service/prompts/maestro-planner.md`.
Its content revision is recorded in `maestro_plan`. Generated plans use the same
sequential execution format; declared workflows bypass planning.

`projects.<id>.maestro_plan_policy` is `review` by default. A submitted run may
explicitly override it with `maestro_plan_policy: "auto"` or `"review"`. Control
configuration preserves the project policy. Browser Settings → Agents and models
provides an override for submitted runs; Project default omits the override.
MCP/automation clients should explicitly request `auto` for unattended planning.
The default review gate is intentionally retained, and step/publication gates
still apply under auto.

## Checkpoints, recovery and retention

Completed outputs are stored atomically under the run's private `maestro/` state.
Bindings cover the workflow revision, the relevant step prefix, resource and
dependency revisions, inputs and prior results. Referenced workflow/resource text
and dependency snapshots remain retained with resumable runs. A changed binding
invalidates the affected checkpoint and downstream outputs and approvals. Source
revisions and input bindings are rechecked after human waits and before effects.

Resume reuses the valid prefix. Re-run from step N creates a child run, keeps valid
earlier checkpoints and creates fresh execution and effect idempotency keys.
An invalidated step that has already published requires an explicit rerun;
unknown/executing effect outcomes in the lineage block recovery until reconciled.
Restart invalidates pending or unused publication approvals through the existing
P3 recovery contract. No automatic redispatch follows an uncertain publication.
Checkpoint retention currently follows run retention; automatic garbage collection
and parallel execution are outside this release.

## HTTP and MCP contracts

All operations require the existing owner/project authorization. Internal recovery
metadata cannot be submitted by clients.

- Submit a standalone workflow using `POST /v1/jobs` with a workflow invocation
  (or palette resource selection), plus optional `workflow_inputs` JSON object.
- `POST /v1/jobs/{job}/resume` accepts optional `workflow_inputs` and planning policy.
- `POST /v1/jobs/{job}/rerun` accepts `from_step` (one based), optional inputs and policy.
- `POST /v1/jobs/{job}/save-workflow` accepts `{ "id": "saved-review" }` after a
  successful completed chain. It writes `workflows/saved-review.json` exclusively,
  without overwriting another workflow or writing into a trusted/pinned catalog.
- MCP exposes `submit_job` with policy/invocation/input fields, `resume_workflow`,
  `rerun_workflow` and `save_chain_as_workflow`.

Recovery requires a terminal source. Denied plans, incomplete steps and unsuccessful
runs cannot be saved as successful chains. Existing identifiers, ownership,
`sem-projeto`, Tailscale names and P3 effect records are preserved. No database
migration is required for the file-backed checkpoints. Refresh packaged assets on
upgrade; version identifiers and bilingual README headings are synchronized.

## Security self-review

Authors and reviewers were distinct. Before final validation, review reproduced
and corrected these findings:

- Incomplete inference could reach an explicit publish request; it now fails
  before preparation. Workflow publication also waits for successful output checks.
- Workflow/resource/input changes during a human wait could leave old authority
  usable. Current source snapshots, actual workspace/media bytes, inherited inputs and fail-closed source
  reads bind dispatch; invalidation revokes unused approvals and prepared effects.
- A whitespace-only workflow revision could reuse a semantic prefix. File-backed
  workflow checkpoints now bind the exact source revision.
- Queued recovery could use a declaration from before a source edit. Dispatch
  reloads the current source and recomputes bindings.
- A rejected generated plan had a completed job envelope and could be saved.
  Saving now requires completed orchestration steps and rejects explicit denial.
- Retained resource bodies could exceed the declaration/payload limit on recovery.
  Declaration normalization strips retained snapshots and rebuilds current bindings.
- Approval edits could drop or forge planner provenance. The authoritative prompt
  revision now comes from the server after applying edited steps.
- Recovery preserves the original conversation context separately from child-run
  lineage; clients cannot forge that internal context pointer.
- YAML alias expansion is bounded before serialization; `safe_load` alone is not
  treated as a resource-exhaustion defense.

The P3 isolation limitation remains: unrestricted same-user shell execution is
advisory, and approval cookies do not create an operating-system isolation boundary.
Only synthetic Jira fixtures and mocked drivers are exercised; no live publication or paid
inference is used for validation.

failed collection (three errors because the workflow module was absent); admission
