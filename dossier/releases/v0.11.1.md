# Version 0.11.1 — Integrated workflows and workspace visual QA

## Behavior and acceptance

This release combines the 0.11.0 declarative workflow and Maestro planning
contracts with the compact workspace established in 0.10.2. The chat retains the
approved mock-4 scale at 100% browser zoom while exposing workflow resources,
planning policy and generated plans in the same shell as the stacked workspace
and resizable Run console.

- The slash palette groups project and trusted-catalog workflows under
  **Workflows**, with the same source, revision and availability information used
  for agents, skills and commands.
- Settings → Agents and models offers Project default, Review before running and
  Auto — run generated plan. Auto bypasses only generated-plan review; step and
  publication approvals keep their existing authority checks.
- A reviewed plan card says that nothing runs before approval and exposes one
  Approve plan & run action. An automatically accepted plan has running state,
  has no approval action and remains inspectable in the Run console.
- Files, Background tasks, Resources and Activity remain stacked in the right
  workspace. Their open state and bounded heights persist locally.
- The Run console preserves resizing, keyboard resizing, maximize/restore and
  the full-height mobile sheet. Existing application scale and overlap guards
  remain enforced.
- The visual matrix covers four viewports, six themes and nine explicit states:
  console closed/open, tour, reviewed plan, automatic plan, publication gate,
  generic slash palette, workflow palette and plan review selector. All visible
  controls must remain in the viewport, uncovered and at least 24 px square.
  Every palette option must also become fully visible and pass hit testing after
  scrolling within the palette.

Workflow schemas, recovery, checkpoint invalidation, effect mediation and HTTP/MCP
contracts remain as specified in [0.11.0](v0.11.0.md). Workspace geometry and
the rationale for preserving scale remain as specified in [0.10.2](v0.10.2.md).

## Migration

No database or server-configuration migration is required. Refresh packaged
browser assets when upgrading. Existing workflow declarations, checkpoints,
project policy, panel preferences and console height remain compatible.

The package, service version endpoint, chat and control labels, Gemini ACP client
information, product tour epoch and both README files advance together to 0.11.1.
Historical 0.10.2 and 0.11.0 release records remain unchanged.

12 subtests passed**, 103 warnings, 60.37 seconds. No Python implementation changed
after this run.
Complete UI run 1: **100/100 spec files passed**, exit 0, on free ports
19294/19295. The runner verified release **0.11.1** through both the service
version endpoint and served HTML before executing tests. The visual matrix
passed **216/216 captures and 15/15 profile scenarios**. No failed-file reruns.
Complete UI run 2: **100/100 spec files passed**, exit 0, on free ports
19394/19395, against the same final implementation. Release **0.11.1** was
verified before testing. The visual matrix again passed **216/216 captures and
15/15 profile scenarios**. No failed-file reruns. Both runs enumerate every
`tests/*.spec.cjs` and `tests/personas/*.spec.cjs` file.
Both full browser runs use `scripts/test-ui.sh` without spec filters, with
`PYTHON` pointing to the checkout virtual environment and `PLAYWRIGHT_MODULE`
to the existing installed Playwright. `TH_ADMIN_PORT` / `TH_CHAT_PORT` select
the port pairs above. `VISUAL_OUTPUT_DIR` and `EVAL_OUTPUT` select separate
evidence directories for each run. Servers and application state are temporary;
no client data or cloud inference is used.

Final conventions check: **0 name errors, 0 name warnings, 0 Portuguese hits**.
README headings are identical, active version identifiers are 0.11.1, changed
JavaScript syntax checks pass, and `git diff --check` is clean. The historical
0.10.2 and 0.11.0 release notes are byte-for-byte unchanged from their branches.

Independent review inspected the merged application, version identifiers, Files
regression and expanded visual assertions. Its functional finding was fixed and
re-reviewed; no correctness, accessibility or complexity findings remain open.
The reviewer did not duplicate the full suites.

Focused integration validation generated **216/216** screenshots and passed
**15/15** seven-profile scenarios. The matrix exercised four viewport sizes, all
six themes and the nine states listed above. It also preserved scale guards for
15 px root text, the 48 px top bar, 300/390 px sidebars and the approximately
65.45 px conversation row.

The first integrated matrix run stopped before capture because its workspace
resource fixture added the workflow but still expected three resources; the
fixture count was corrected to four. The next run exposed a visual-helper defect
at 1280 × 720: options below a valid scrollport were treated as visible and then
reported as covered by the composer. Measured geometry showed the palette ending
at 550 px and the prompt starting at 558 px, so there was no product overlap.
The helper now accounts for clipping ancestors, and a stronger assertion scrolls
every palette option fully into the menu and hit-tests it. The final focused run
passed all 216 states and 15 scenarios. No product CSS assertion was removed or
weakened for this correction.

Independent integration review then found an obsolete exclusive-pane condition:
when a returning browser had saved `right-panel-view=activity`, the now-stacked
Files section was visible but its root request was skipped. A regression seeded
that legacy preference and first failed waiting for the first file tree item.
File-root loading now depends only on the workspace being open, including the
startup path; the saved shortcut target no longer suppresses another visible
section. The focused Files/Activity browser scenario passed after the fix.

The campaign uses synthetic fixtures and automated Chromium. It is not research
with human participants, screen-reader certification, live provider inference or
proof of third-party authentication. Token and cost metrics are unavailable, so
no efficiency claim is made.
