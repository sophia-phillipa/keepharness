# 0.15.0 — KeepHarness: Space pages, scheduled tasks, a desktop client and the gauntlet hardening

## Behavior

The product is renamed from Tail Harness to **KeepHarness**, and the chat gains the Codex desktop's Space and Scheduled concepts, a detail view for each connector and plugin, and an Electron client. The release candidate then went through the 0.15.0 gauntlet; part of its Wave 1 and Wave 2 fixes ship here (the rest is listed under Known limits) (decisions D01–D54, accepted by Sophia on 2026-10-03).

### Rename, migration and brand

- **Rename**: the product name, package and console scripts (`keepharness`, `keepharness-install`, `keepharness-mcp`, `keepharness-local`), the MCP server name, the icon, the systemd unit and launcher, the environment variables (`KEEPHARNESS_*`), the state folder (`~/.local/share/keepharness`), the client config folder (`~/.config/keepharness`), the shared UI package (`harness_ui`, browser globals `HarnessUI` and `HarnessTheme`) and the repository (`https://github.com/sophia-phillipa/keepharness`) all use the new name. The old `TAIL_HARNESS_*` variables are not read any more; the admin logs one warning per such variable still set when it starts, naming its `KEEPHARNESS_*` replacement.
- **Harness agents** (formerly "Tail agents"): the API is `/v1/harness-agents`, resource ids are `harness/agents/<id>`, the scope and origin are `harness`, the folder is `harness-agents/` and the error codes are `harness_agent_*` (`harness_resources_unavailable` for an unselected `@@` marker). Calling an agent with `@@name` is unchanged. Editing an agent no longer breaks its conversation (the carried-over selection follows the new revision), and ending an agent conversation tells the provider the persona is over.
- **Install transaction** (D21–D24): `install.sh` is the only thing that moves Tail Harness state. It refuses inside a container, preflights a wheel built from a copy of the source tree in a temporary venv, and only then stops `tail-harness.service`, moves the state and builds the real environment; the service runs the installed wheel. `./install.sh --merge-legacy [--apply]` heals a state an earlier pre-release split between two folders, and `./install.sh --rollback-to-0.14` gives the state back to 0.14 (see Migration).
- **Brand** (D51): the "Design 2" mark — a navy squircle with a coral ring broken where three teal nodes, joined in a triangle, sit. One geometry in `scripts/brand-assets.cjs` generates both SVG marks, the sprite symbol, the icon set (16–512 px, `.ico`, `.icns`, favicon, Apple touch icon) and the splash; the harness rail and the admin header show the same mark.

### Space, Scheduled and plugins

- **Space › Pages**: private Markdown pages next to a project's conversations, with a title and body editor (Ctrl/⌘ S, preview with the chat's renderer), **Attach to message**, **Start chat with this page** and a two-step delete. Closing, Esc, a project switch, opening another page and Attach/Start chat save first; a failed save keeps the text open with the error, and a lost connection no longer closes Space, Scheduled or the agent editor. API: `GET/POST /v1/pages`, `GET/PUT/DELETE /v1/pages/{id}`.
- **Scheduled tasks**: recurring prompts (daily, weekly or every N hours, in local time) with project, provider, model, effort and access (Ask or Read only; `auto` and `full` are refused). A background check every 30 s submits each due task once, as its owner, through the same path as `POST /v1/jobs`; it never catches up missed runs and defers while the harness is busy (`queue_full`, `owner_queue_full`, `submission_rate_limit`); any other refusal, such as `job_storage_limit`, is a failure. A run replayed after a crash whose prompt was edited in between records the job it already submitted instead of failing on `idempotency_conflict`. Conversations started by a task carry a **Scheduled** label. API: `GET/POST /v1/schedules`, `PUT/DELETE /v1/schedules/{id}`, `POST /v1/schedules/{id}/run`.
- **Unattended scheduled runs** (D15): a scheduled run never waits for a person: an action that needs approval (or a workflow gate) is denied at once (`unattended`), the run goes on and is flagged "needs you". The scheduler reads each run's outcome back (`last_run.state` is `completed`, `failed`, `cancelled` or `interrupted`), counts failed, cancelled and interrupted runs toward the three-in-a-row pause, skips a due time while the previous run is still active, and raises attention items (`schedule_alerts` in `GET /v1/activity`) for paused tasks and flagged runs. Scheduled › Last run shows the real state and opens the run.
- **Plugin detail**: each row of the Plugins panel opens what the connector or plugin is, whether this conversation may use it and why not, its install status, its use in this project and the approval note. Remote ChatGPT plugins are reported as not available in Codex and DeepSeek runs, which turn Codex apps off (D48).

### Desktop client

`desktop/` (Electron 44.4.1) starts the local admin when it is not running, opens the harness (or the admin when no provider is ready) in a sandboxed window and sends other links to the system browser; an admin it started stops when it quits, one already running is left alone. `KEEPHARNESS_PYTHON`, `KEEPHARNESS_ADMIN_PORT` and `KEEPHARNESS_PORT` configure it. `scripts/package-desktop-linux.sh` builds a portable Linux package (`dist/keepharness-<version>-linux-x64/`, from an Electron runtime already on disk, with a `build-manifest.json`), and `desktop/linux/install-desktop-linux.sh` installs it under `~/.local/opt/keepharness-<version>` with a menu entry, refusing to overwrite the same version. The backend stays the Python that `install.sh` installed (D17 A: for computers where `install.sh` ran). The main process signs the window in as the owner and enrolls it for approvals (see Security); the window may write to the clipboard and raise notifications for its own `127.0.0.1` origins only.

### Security

- **Access modes** (D10, D12): Automatic and Full access are for the owner on this computer only; any other identity (the vpn key, a tailnet login) gets `403 access_mode_owner_only` and its runs have no shell, hooks or host connectors. Read only turns every connector and plugin off on Codex, DeepSeek and Claude; Codex and DeepSeek read through the harness reader (`harness_reader`: read, list and search inside the project folders and the conversation's attachment text, nothing else; it refuses hidden credential files, the MCP bridge's credential list and symbolic links, and opens files one folder at a time). In Ask, Codex and DeepSeek show an approval card before every connector call. The access menu says what each mode does on each provider; Automatic is still unrestricted on Codex, DeepSeek and Claude (see Known limits).
- **Run folders outside the state**: provider run folders live in `~/.local/share/keepharness-sessions`, so no run has the state folder (keys, databases) among its parents.
- **Local owner** (D09, D13 A): a per-install secret (`<state>/local.key`, 0600; only its SHA-256 goes into `runtime.json`) signs one-time `/open` tickets and never leaves the disk. `keepharness open` opens a link that gives this browser its own owner session: the `keepharness-local` cookie holds a random token, and `local-sessions.json` (0600, at most 64 entries, 30 days each) keeps only its SHA-256 and expiry; `keepharness open --revoke` signs every browser out. The admin's `/api/*` answers 401 without a listed session. The desktop main process redeems its own ticket and gives the window only the session.
- **Host and Tailscale**: one Host allow-list (`host_allowed`) serves the admin and the harness; a `Tailscale-User-Login` request whose Host is outside the configured origins gets 403 `host_denied`. A tailnet login is mapped only on Tailscale Serve's proxy hop (Host equal to `browser_url`'s, a matching `X-Forwarded-Host`, one tailnet `X-Forwarded-For`) and never when `browser_url` is loopback.
- **Owner-only actions**: starting, stopping or restarting a host service (`POST /v1/services`) needs an enrolled approval session and the local owner (`403 service_control_denied`); registering, editing or deleting project folders and listing host directories answer 403 `project_management_local_only` to anyone else; saving a project workflow answers 403 `workflow_save_local_only`. Registered projects reach other clients only when `shared_projects` is on (default off). Denying a Codex question sends no typed answers. The MCP bridge's `upload_path` reads only inside the `upload_roots` listed in `client.json`, refuses credential stores and asks the person to confirm path, file count and size before sending.
- **Redaction**: for clients other than the local owner, `GET /v1/harness-agents` returns only name, backend, model, effort and availability, and `/v1/resources` and `/v1/catalog` replace absolute `source` paths with the logical `resource_id`. Provider error details are one line, redacted and bounded.
- **Bounded search**: `GET /v1/conversations?q=` answers 400 `search_query_too_short` under two characters and 429 `search_rate_limit` above 60 searches a minute per client, reads at most the 500 newest conversations and 16 MiB of stored text off the event loop, and adds `"limited": true` when it stopped early.
- **Approval enrollment**: a `403 approval_session_required` answer carries `owner` (and `login` for a tailnet identity), so the browser shows the exact `keepharness approve-device --owner <id>` command or tells a guest to ask the owner.

See `docs/local-owner-access.md`.

### Providers

- **Harness-owned provider homes** (D01, D02; `docs/provider-homes.md`): Codex, DeepSeek and Claude Code run in homes under the control state folder (`<state>/providers/…`, 0700), not in the owner's `~/.codex` and `~/.claude`. Settings › Providers › Log in / Renew access signs in inside those homes; sessions stay there, and nothing is written under `~/.codex/sessions` or `~/.claude/projects`. Provider processes get only an allow-listed environment (`PATH`, `HOME`, locale, proxy and CA variables, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, plus the DeepSeek key and vault injections): `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` and every other `CLAUDE_CODE_*` variable are no longer forwarded.
- **Personal setup, off by default**: the top-level `personal_setup` setting (default `false`) replaces `services.claude.global_hooks`. When the owner turns it on, only the owner's own attended conversations get the owner's MCP servers and plugins, hooks (with the hooks grant) and `AGENTS.md` / `CLAUDE.md`; guests and scheduled runs never do.
- **Unsigned providers are quarantined**: an enabled Codex or Gemini service that is not signed in (or whose CLI is missing) no longer stops the harness: its models go offline with "Sign in required" (`unavailable_models`), the other providers keep working, and signing in then applying the settings brings it back. A Codex model the provider's catalog no longer returns takes only its own route offline the same way (`unavailable_models`, saved selection kept).
- **Answer language** (D30, rule A): every provider's instructions carry "Answer in the language of the user's latest message unless they ask otherwise."
- **Lost threads and large attachments**: a Codex or DeepSeek thread whose rollout is gone ("no rollout found") now maps to `native_session_missing`, sets `native-thread.json` aside and replays the harness history on a fresh thread once, as Claude and Gemini already did; the replay does not run hooks or stream the attachment notice twice. The app-server reader limit follows the attachment cap (4/3 of it plus 8 MiB) and `thread/resume` sends `excludeTurns: true`, so a large photo or a long thread no longer breaks a conversation; a longer line fails as `<provider>_output_limit`.
- **Error messages per provider**: Codex's own retry notices (`willRetry`) no longer abort a run (`provider_retrying`); provider messages travel with the error. DeepSeek 401/402 read as a key or balance problem instead of "Codex stopped"; Claude maps every error kind (usage limit, overloaded, retired model, rate limit, sign-in) to its own guidance and reports a context meter that counts cached input; Gemini keeps its session on a login or quota error, carries the provider's message and turns a stalled handshake into `provider_idle_timeout`. Stored error codes change: JSON-RPC failures are `<provider>_execution_failed: <message>`, and DeepSeek and local runs report `deepseek_*` / `local_*` codes. Maestro reports the planner plus every step as the run's usage.

### Queue and approvals

- **Provider capacity and approval waits** (D14): a run waiting for an approval or a gate frees its provider lane and inference slot, and takes them back, ahead of new runs, once the decision arrives; a local model keeps both (its GPU). Cloud providers run two conversations at once unless `services.<provider>.max_concurrent` says otherwise; local and Maestro keep one. The admin keeps `max_concurrent` and the root `approval_timeout_seconds` / `approval_max_consecutive_expirations` across saves and writes them to `runtime.json`.
- **Stop with queued follow-ups** (D16): Stop (or Discard) keeps the stopped turn's queued follow-ups waiting (`queue_wait` reason `held_after_stop`, `held_followups` in the cancel answer) until **Run queued message** (`POST /v1/jobs/{id}/run-queued`, refused for a deleted conversation and run in one transaction) or **Discard** (`POST /v1/jobs/{id}/cancel`).

### Chat and layout

- **Chat polish** (`docs/chat-polish.md`): **Copy** on every answer and code block, **Ask again** on the newest answer; wide tables and code scroll inside their own region; search inside prompts and answers with snippets and no internal ids; conversations without a title are named by the first sentence of their first prompt; OS notifications and a "needs you" count in the window title while the window is unfocused (D35); canonical provider names (Codex, Claude Code, DeepSeek, Local models, Maestro, D42) and friendly model names derived from identifiers, older Claude models under "More models", a note when a message goes to another provider, a fresh model choice on the provider's default effort; plain words instead of protocol names in chips, cards and the status strip; "Worked for" leaves out queue time; a visible draft limit (150,000 UTF-8 bytes), attachment sizes and the 20-file limit; an idle tab makes about 30 requests a minute.
- **Composer layout**: the agent card has its own row above the input, access, effort and Send never shrink (the model label ellipsizes; below a 380 px pane model and effort wrap to a second line), the placeholder is "Send a message, or / for agents and skills", and the status-strip toggle stays on one line. The resize handles are drawn thin but keep an invisible 24 px hit zone that covers no control.
- **Layout-lint gate** (`tests/layout-lint.spec.cjs`, `docs/layout-lint.md`): composer, status strip, side panel, console, search and Setup screens at 1440 to 360 px wide (plus 800x600 and 720x500 windows), in Paper and Graphite, fail on overlapping controls, text that escapes its box, clipped fields, horizontal page scroll and the named invariants V1–V6 and V12; it runs with every `scripts/test-ui.sh`.
- **Admin**: "Open harness" points at the harness's real address and is disabled while the harness is stopped.

### Operator suite

`scripts/operator-suite.sh` (`tests/operator/`, `docs/operator-suite.md`) operates the app the way a person does, area by area (shell, sidebar, new chat, composer, conversation, run console, approvals, agents, Space, Scheduled, plugins, files, settings, admin, keyboard, window sizes, themes, desktop), with a caption, assertion, screenshot and layout lint per step. Fixture mode uses isolated servers with fake Claude and Gemini CLIs and never calls a cloud model; `--visible`, `--target desktop` and a budgeted `--mode real` exist. Steps that hit a defect still open are listed in `tests/operator/known-defects.json` with their ledger id.

## Acceptance criteria

1. No product-facing string, identifier, package, script, path or environment variable keeps the old name; `rg -i "tail[ _-]?harness|tail_ui|TailUI|TailTheme"` finds only release notes before 0.15.0 and the migration code, tests and comments that name the old paths on purpose. Tailscale names and the `sem-projeto` protocol id are unchanged.
2. Only `install.sh` moves the state, after its preflight (D24). `~/.local/share/tail-harness` moves to `~/.local/share/keepharness` when the new folder does not exist and the old one is unmarked or marked as Tail Harness (or already adopted); its identity markers stay `{"slug":"tail-harness","lineage":"tail-harness"}` (an unmarked folder gets that marker), which KeepHarness opens as its own, and the absolute paths in `runtime.json` follow the move through an atomic write. `~/.config/tail-harness` moves to `~/.config/keepharness` under the same rule. The move holds a lock (`~/.local/share/tail-harness.migration.lock`, removed once nothing is left to move) and is refused while the old state is in use (a port named in the old `runtime.json` answers on 127.0.0.1, a process has files open in it, or the running Python lives inside it), except by `tail-harness.service` and its processes, which `install.sh` stops itself right after the preflight; it is also refused while the rollback record exists, and a move the system refuses (`EXDEV`, `EBUSY`) is refused the same way, never a crash. A server start (`keepharness`, `python -m control`, boot, the desktop client) and `approve-device` with the default state refuse while the old folder still waits, before anything creates `~/.local/share/keepharness`, and name what to do. An existing new folder is never merged into automatically; the one exception is a new folder that holds nothing but a client MCP bridge (`venv/` and `mcp_bridge.py`, left by the pre-release `setup-mcp.sh`), which is renamed aside as `keepharness.bridge-<timestamp>` (nothing is deleted) so the Tail Harness state moves into its place. A folder of another identity is left alone, a fork never takes Tail Harness state, an explicit `--state` folder is used in place, and `--scan` never moves anything.
3. `install.sh` first refuses inside a container (`/run/.containerenv` or `CONTAINER_ID`; run it on the host or through `distrobox-host-exec`), on an admin port another program holds (naming its pid and command) and on Tail Harness state that is in use outside its unit or rolled back, then builds a wheel from a copy of the source tree (tracked plus untracked, not ignored, files when the tree is its own git repository; a filtered copy otherwise), installs it in a temporary venv and runs `control.install_check`; only after that preflight does it stop the old `tail-harness.service`, move the state and create the real virtual environment, so a missing `ensurepip`, a failed build or an offline dependency leaves nothing stopped or moved. `install.sh --check-only` is that preflight alone and passes while the old state still waits to move. The service runs the installed wheel (`--dev` installs the checkout editable and records it in the unit); the unit carries the installer's `PATH`, `StartLimitBurst`/`StartLimitIntervalSec` and no `network-online.target`, and `keepharness-install` reports success only when the unit's own process answers on the port. The admin checks its port before any startup work, and the build regenerates only files that differ. A virtual environment that moved with the state folder is rebuilt (`venv --clear`), the old `tail-harness` distribution is uninstalled from it so its console scripts disappear, and the package is reinstalled; `keepharness-install` disables the old unit and removes its unit file, launcher and menu entry before installing the new ones.
4. At service startup the agents folder `tail-agents/` moves to `harness-agents/` when only the old one exists; a follow-up turn of a persona started before the upgrade (stored as `tail/agents/<id>`) keeps answering as `harness/agents/<id>`.
5. A settings bundle exported by Tail Harness (`format: "tail-harness-settings"`) still imports; any other foreign format is refused.
6. A theme chosen before the rename (`tail-harness:theme:*` in the browser) is kept on the first paint; the new key wins once it exists.
7. Provider processes still never inherit `TAIL_HARNESS_*` variables, and integrations may not declare them.
8. Claude Code and Gemini key their native sessions by working directory, so a "No project" conversation whose folder moved cannot be resumed. When `claude --resume` reports the session missing, or Gemini's `session/load` fails because the session is gone, the adapter sets the stored `claude-session.json` / `gemini-session.json` aside (`*.before-session-missing`) and the turn runs once more in a fresh native session seeded with the harness's own history, the same path as a provider switch. Codex and DeepSeek do the same for "no rollout found" (`native-thread.json`). Nothing under `~/.claude/projects` or `~/.gemini` is renamed (`tests/test_native_session_missing.py`).
9. Space, Scheduled, plugin detail and the desktop navigation policy pass their own suites; the full Python and UI suites pass with coordinated version identifiers (`pyproject.toml`, `agent_service/VERSION` and `desktop/package.json` all say 0.15.0).
10. `setup-mcp.sh` run against a scratch `HOME` that already holds a server state folder changes nothing under `~/.local/share/keepharness` and installs the bridge under `~/.local/share/keepharness-mcp`; a fork's generated installer uses `<its state folder>-mcp`.
11. A configured Codex model missing from the fresh catalog (retired, hidden or no longer entitled) no longer stops the harness from starting: only that route is unavailable, including when it is the default MCP model, and Gemini keeps refusing a missing model as before. An enabled Codex or Gemini service that is not signed in is quarantined the same way (`tests/test_unsigned_provider_quarantine.py`).
12. A vpn-key or tailnet identity that submits `auto` or `full` gets 403 `access_mode_owner_only`, and the Codex settings built for its Ask run have no `danger-full-access`, no `approvalPolicy: never` and no enabled host connector. In Read only, no host connector or plugin is enabled on Codex, DeepSeek or Claude, and the harness reader refuses any path outside the authorized roots, hidden credential files and symbolic links. No run folder has the state folder among its parents (`tests/test_run_workspace_isolation.py`, `tests/test_approval_policy.py::test_mcp_gating_matrix`, `tests/test_approval_authority.py`).
13. With `max_concurrent: 1`, a second run on the same provider dispatches and completes while the first waits for an approval, and the first takes its lane and slot back only when they are free; cancelling a parked run leaves both counters balanced (`tests/test_approval_parking.py`). An admin save that omits `max_concurrent` or the approval keys keeps them (`tests/test_control_persistence.py`). A scheduled run's due time is skipped while the previous run is active; failed, cancelled and interrupted runs count toward the pause; `last_run.state` is the real outcome (`tests/test_scheduler.py`); unattended approvals and gates are denied at once (`tests/test_unattended_approvals.py`); Stop holds queued follow-ups until run or discarded (`tests/test_followup_hold.py`).
14. After a Codex, DeepSeek and Claude turn nothing is written under the owner's `~/.codex` or `~/.claude`, a child process sees only the allow-listed environment, and the personal setup reaches only the owner's own attended conversations (`tests/test_env.py`, `tests/test_scoped_home_security.py`, `tests/test_hook_scope.py`).
15. A loopback request without a listed owner session is not `local`; a cookie holding the raw install secret is refused; `/open` admits one browser once; `keepharness open --revoke` signs every browser out; a tailnet login maps only on Serve's hop and never with a loopback `browser_url`; project management, service control and workflow saves are refused to non-owners; guest views carry no host paths (`tests/test_api_security.py`, `tests/test_admin_security.py`, `tests/test_client_authority.py`, `tests/test_mcp_bridge_upload.py`, `desktop/policy.test.cjs`).
16. A 3 MiB app-server line does not kill a run, `willRetry` notices do not abort it, and DeepSeek 401/402 and every Claude error kind get their own message (`tests/test_adapters.py`, `tests/test_deepseek.py`, `tests/test_claude_errors.py`, `tests/test_gemini.py`, `tests/test_usage_stream.py`).
17. `--merge-legacy` on a split fixture with a real SQLite database lists its plan without changing anything, applies it with a backup and integrity-checked copies, and refuses on two databases, a colliding conversation or a folder in use; `--rollback-to-0.14` refuses when the old folder exists, sets thread markers aside and writes the rollback record (`tests/test_state_merge.py`, `tests/test_product_identity.py`, `tests/test_install_script.py`, `tests/test_install_service.py`).
18. `tests/layout-lint.spec.cjs` passes on every screen, width and theme with only the three `KNOWN_NOISE` entries, and each resize handle keeps a 24 px hit zone (`tests/support/handle-hit-zone.cjs`); the chat-polish specs named in `docs/chat-polish.md` pass.
19. The operator suite in fixture mode passes every area, with failures only on the steps listed in `tests/operator/known-defects.json`.

## Migration

- **State**: only `install.sh` moves it, after its preflight (D24); a server start (`keepharness`, `python -m control`, boot, the desktop client) and `approve-device` with the default `--state` refuse while the old folder waits, and `--scan` never moves it. `install.sh` stops a running `tail-harness.service` itself; a Tail Harness started any other way (a terminal, the desktop client) must be stopped first, and the message names the pid and command that hold the port. A systemd unit or script that passes `--state ~/.local/share/tail-harness` explicitly keeps working in place; reinstall to move it. Moving the state moves a virtual environment kept inside it (`install.sh` layout); `install.sh` rebuilds it and reinstalls the package.
- **Live 0.14 from the main checkout**: if Tail Harness 0.14 runs from the checkout you merge or pull 0.15.0 into, its UI and build change underneath it; stop it, or run 0.14 from a pinned worktree, before updating that checkout.
- **Both folders exist** (for example after an earlier pre-release start split them): `install.sh` moves nothing, unless the new folder holds only a client MCP bridge, which is set aside so the old state can move (acceptance criterion 2), and logs a warning naming both folders. Heal the split with `./install.sh --merge-legacy`, which prints a merge plan and changes nothing; `--apply` refuses while either folder is in use, without enough free space, when both hold a conversation database or when one conversation's sessions or uploads exist in both, then writes a 0600 tar backup of both folders (environments excluded) to `~/.local/share/keepharness-merge-<stamp>.tar`, copies `jobs.sqlite3` and `approval_sessions.sqlite3` with SQLite's online backup (integrity and job counts checked, never overwriting), copies everything else `tail-harness/` lacks, keeps `tail-harness/`'s settings, keys and `runtime.json`, appends the audit logs (one record per line), marks `runs/` as Tail Harness state and renames `keepharness/` to `keepharness.split-<stamp>` (never deleted). The merged folder opens in 0.14.0; `./install.sh` then moves it. To undo an applied merge, move `~/.local/share/tail-harness` aside and rename `keepharness.split-<stamp>` back, or extract the backup.
- **Rollback to 0.14.0**: `./install.sh --rollback-to-0.14` refuses when `~/.local/share/tail-harness` already exists (it never nests or merges) or the state belongs to another identity, disables and removes `keepharness.service`, its launcher and menu entry, and refuses while any process still uses the state. It then deletes the 0.15 environment (`venv/`), renames `runs/harness-agents` to `runs/tail-agents`, renames every provider thread marker under `runs/sessions` (`native-thread.json`, `remote-thread.json`, `claude-session.json`, `gemini-session.json`) to `*.before-rollback` so 0.14 replays the harness history instead of resuming a pre-upgrade thread and losing the 0.15 turns, resets a KeepHarness identity marker to the Tail Harness value, moves the state and config folders back with `runtime.json` rewritten, and writes `~/.local/share/tail-harness.rolled-back`. While that record exists nothing moves to KeepHarness again and KeepHarness refuses to start on the default state; delete it and run `./install.sh` to upgrade again. Agents selected in conversations started on 0.15.0 (`harness/agents/<id>`) are unknown to 0.14.0.
- **Sign in to Codex and Claude again**: the providers now run in KeepHarness's own homes, so the login in your `~/.codex` and `~/.claude` is not used. After upgrading, use Settings › Providers › Log in / Renew access for Codex and Claude Code. Until then Codex (and Gemini) models are offline with "Sign in required" while the other providers start. `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` in the service environment are no longer passed to providers.
- **Personal setup**: runs no longer see your own Codex/Claude MCP servers, plugins, hooks, `AGENTS.md` or `CLAUDE.md`. To get them back in your own conversations, set `"personal_setup": true` at the top level of `~/.local/share/keepharness/settings.json` (there is no switch in the admin panel yet). `services.claude.global_hooks` is dropped on the next save; it is not converted.
- **Run folders**: provider run folders now live in `~/.local/share/keepharness-sessions`. The old ones under `~/.local/share/keepharness/runs/sessions` are left in place and no longer used: the next turn of every existing conversation starts a new native thread from the harness history. Remove the old folder once you no longer need it.
- **Native sessions**: the first turn of an existing "No project" Claude or Gemini conversation after the move starts a fresh native session from the harness history (see acceptance criterion 8); later turns resume that new session.
