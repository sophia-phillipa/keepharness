# 0.15.0 — KeepHarness: Space pages, scheduled tasks and a desktop client

## Behavior

The product is renamed from Tail Harness to **KeepHarness**, and the chat gains the Codex desktop's Space and Scheduled concepts, a detail view for each connector and plugin, and an Electron client.

- **Rename**: the product name, package and console scripts (`keepharness`, `keepharness-install`, `keepharness-mcp`, `keepharness-local`), the MCP server name, the icon, the systemd unit and launcher, the environment variables (`KEEPHARNESS_*`), the state folder (`~/.local/share/keepharness`), the client config folder (`~/.config/keepharness`), the shared UI package (`harness_ui`, browser globals `HarnessUI` and `HarnessTheme`) and the repository (`https://github.com/sophia-phillipa/keepharness`) all use the new name. The old `TAIL_HARNESS_*` variables are not read any more; the admin logs one warning per such variable still set when it starts, naming its `KEEPHARNESS_*` replacement.
- **Harness agents** (formerly "Tail agents"): the API is `/v1/harness-agents`, resource ids are `harness/agents/<id>`, the scope and origin are `harness`, the folder is `harness-agents/` and the error codes are `harness_agent_*` (`harness_resources_unavailable` for an unselected `@@` marker). Calling an agent with `@@name` is unchanged.
- **Space › Pages**: private Markdown pages next to a project's conversations, with a title and body editor (Ctrl/⌘ S, preview with the chat's renderer), **Attach to message**, **Start chat with this page** and a two-step delete. API: `GET/POST /v1/pages`, `GET/PUT/DELETE /v1/pages/{id}`.
- **Scheduled tasks**: recurring prompts (daily, weekly or every N hours, in local time) with project, provider, model, effort and access (Ask or Read only). A background check every 30 s submits each due task once, as its owner, through the same path as `POST /v1/jobs`; it never catches up missed runs, pauses after three failures in a row and defers while the harness is busy (`queue_full`, `owner_queue_full`, `submission_rate_limit`); any other refusal, such as `job_storage_limit`, is a failure. A run replayed after a crash whose prompt was edited in between records the job it already submitted instead of failing on `idempotency_conflict`. Conversations started by a task carry a **Scheduled** label. API: `GET/POST /v1/schedules`, `PUT/DELETE /v1/schedules/{id}`, `POST /v1/schedules/{id}/run`.
- **Plugin detail**: each row of the Plugins panel opens what the connector or plugin is, whether this conversation may use it and why not, its install status, its use in this project and the approval note. Remote ChatGPT plugins are reported as not available in Codex and DeepSeek runs, which turn Codex apps off.
- **Approval enrollment**: a `403 approval_session_required` answer carries `owner`, the caller's own owner id, so the browser can show the exact `keepharness approve-device --owner <id>` command.
- **Access modes**: Automatic and Full access are for the owner on this computer only; any other identity (the vpn key, a tailnet login) gets `403 access_mode_owner_only` and its runs have no shell, hooks or host connectors. Read only turns every connector and plugin off on Codex, DeepSeek and Claude; Codex and DeepSeek read through the harness reader (`harness_reader`: read, list and search inside the project folders and the conversation's attachment text, nothing else). In Ask, Codex and DeepSeek show an approval card before every connector call. Run folders move out of the state folder to `~/.local/share/keepharness-sessions`. The access menu says what each mode does on each provider; Automatic is still unrestricted on Codex, DeepSeek and Claude.
- **Provider capacity and approval waits** (D14): a run waiting for an approval or a gate frees its provider lane and inference slot, and takes them back, ahead of new runs, once the decision arrives; a local model keeps both (its GPU). Cloud providers run two conversations at once unless `services.<provider>.max_concurrent` says otherwise; local and Maestro keep one. The admin keeps `max_concurrent` and the root `approval_timeout_seconds` / `approval_max_consecutive_expirations` across saves and writes them to `runtime.json`.
- **Unattended scheduled runs** (D15): a scheduled run never waits for a person: an action that needs approval is denied (`unattended`), the run goes on and is flagged "needs you". The scheduler reads each run's outcome back (`last_run.state` is `completed`, `failed`, `cancelled` or `interrupted`), counts the last three toward the three-in-a-row pause, skips a due time while the previous run is still active, and raises attention items (`schedule_alerts` in `GET /v1/activity`) for paused tasks and flagged runs. Scheduled › Last run shows the real state and opens the run.
- **Stop with queued follow-ups** (D16): Stop (or Discard) keeps the stopped turn's queued follow-ups waiting (`queue_wait` reason `held_after_stop`, `held_followups` in the cancel answer) until **Run queued message** (`POST /v1/jobs/{id}/run-queued`) or **Discard** (`POST /v1/jobs/{id}/cancel`).
- **Desktop client** (`desktop/`, Electron 44.4.1): starts the local admin when it is not running, opens the harness (or the admin when no provider is ready) in a sandboxed window and sends other links to the system browser. `KEEPHARNESS_PYTHON`, `KEEPHARNESS_ADMIN_PORT` and `KEEPHARNESS_PORT` configure it. No packaged build yet.
- **Upgrade and startup safety**: `setup-mcp.sh` installs the client MCP bridge (and its virtual environment) in its own folder, `~/.local/share/keepharness-mcp`, never in the state folder, so it can no longer make the next upgrade open an empty KeepHarness or rewrite the running service's venv. A Codex model that the provider's catalog no longer returns takes only its own route offline: it is dropped from that run's routes, listed under `unavailable_models` in `runtime.json` with its reason and logged as a warning, and the saved selection is kept for repair; Claude, DeepSeek and the other Codex models still start.

## Acceptance criteria

1. No product-facing string, identifier, package, script, path or environment variable keeps the old name; `rg -i "tail[ _-]?harness|tail_ui|TailUI|TailTheme"` finds only release notes before 0.15.0 and the migration code, tests and comments that name the old paths on purpose. Tailscale names and the `sem-projeto` protocol id are unchanged.
2. When the server starts with the default state folder (and in `install.sh`), `~/.local/share/tail-harness` moves to `~/.local/share/keepharness` when the new folder does not exist and the old one is unmarked or marked as Tail Harness (or already adopted); its identity markers stay `{"slug":"tail-harness","lineage":"tail-harness"}` (an unmarked folder gets that marker), which KeepHarness opens as its own, and the absolute paths in `runtime.json` follow the move through an atomic write. `~/.config/tail-harness` moves to `~/.config/keepharness` under the same rule. The move holds a lock (`~/.local/share/tail-harness.migration.lock`, removed once nothing is left to move) and is refused while `tail-harness.service` is active, while a port named in the old `runtime.json` (`port`, `admin_url`) answers on 127.0.0.1, or while the running Python lives inside the old folder; a move the system refuses (`EXDEV`, `EBUSY`) is refused the same way, never a crash. A refused move prints why and asks to stop Tail Harness and run `./install.sh`; the server then exits non-zero before anything creates `~/.local/share/keepharness` (the desktop client shows that message), and `install.sh` stops. An existing new folder is never merged into: each start logs a warning naming both folders and how to recover. The one exception is a new folder that holds nothing but a client MCP bridge (`venv/` and `mcp_bridge.py`, left by the pre-release `setup-mcp.sh`): it holds no state, so it is renamed aside as `keepharness.bridge-<timestamp>` (nothing is deleted, a warning names it) and the Tail Harness state moves into its place; an empty folder, or one that also holds any state file, is left as it is. A folder of another identity is left alone, a fork never takes Tail Harness state, an explicit `--state` folder is used in place (nothing moved), and other subcommands (`approve-device`, `--scan`) never move anything; `approve-device` with the default state refuses while the old folder still waits to move.
3. `install.sh` first refuses inside a container (`/run/.containerenv` or `CONTAINER_ID`; run it on the host or through `distrobox-host-exec`), on an admin port another program holds (naming its pid and command) and on Tail Harness state that is in use or rolled back, then builds a wheel from a copy of the tracked files, installs it in a temporary venv and runs `control.install_check`; only after that preflight does it stop the old `tail-harness.service`, move the state and create the real virtual environment, so a missing `ensurepip`, a failed build or an offline dependency leaves nothing stopped or moved. `install.sh --check-only` is that preflight alone and passes while the old state still waits to move. The service runs the installed wheel (`--dev` installs the checkout editable and records it in the unit); the unit carries the installer's `PATH`, `StartLimitBurst`/`StartLimitIntervalSec` and no `network-online.target`, and `keepharness-install` reports success only when the unit's own process answers on the port. The admin checks its port before any startup work, and the build regenerates only files that differ. A virtual environment that moved with the state folder is rebuilt (`venv --clear`), the old `tail-harness` distribution is uninstalled from it so its console scripts disappear, and the package is reinstalled; `keepharness-install` disables the old unit and removes its unit file, launcher and menu entry before installing the new ones.
4. At service startup the agents folder `tail-agents/` moves to `harness-agents/` when only the old one exists; a follow-up turn of a persona started before the upgrade (stored as `tail/agents/<id>`) keeps answering as `harness/agents/<id>`.
5. A settings bundle exported by Tail Harness (`format: "tail-harness-settings"`) still imports; any other foreign format is refused.
6. A theme chosen before the rename (`tail-harness:theme:*` in the browser) is kept on the first paint; the new key wins once it exists.
7. Provider processes still never inherit `TAIL_HARNESS_*` variables, and integrations may not declare them.
8. Claude Code and Gemini key their native sessions by working directory, so a "No project" conversation whose folder moved cannot be resumed. When `claude --resume` reports the session missing, or Gemini's `session/load` fails, the adapter sets the stored `claude-session.json` / `gemini-session.json` aside (`*.before-session-missing`) and the turn runs once more in a fresh native session seeded with the harness's own history, the same path as a provider switch. Nothing under `~/.claude/projects` or `~/.gemini` is renamed.
9. Space, Scheduled, plugin detail and the desktop navigation policy pass their own suites; the full Python and UI suites pass with coordinated version identifiers.
10. `setup-mcp.sh` run against a scratch `HOME` that already holds a server state folder changes nothing under `~/.local/share/keepharness` and installs the bridge under `~/.local/share/keepharness-mcp`; a fork's generated installer uses `<its state folder>-mcp`.
11. A configured Codex model missing from the fresh catalog (retired, hidden or no longer entitled) no longer stops the harness from starting: only that route is unavailable, including when it is the default MCP model, and Gemini keeps refusing a missing model as before.
12. A vpn-key or tailnet identity that submits `auto` or `full` gets 403 `access_mode_owner_only`, and the Codex settings built for its Ask run have no `danger-full-access`, no `approvalPolicy: never` and no enabled host connector. In Read only, no host connector or plugin is enabled on Codex, DeepSeek or Claude, and the harness reader refuses any path outside the authorized roots, hidden credential files and symbolic links. No run folder has the state folder among its parents.
13. With `max_concurrent: 1`, a second run on the same provider dispatches and completes while the first waits for an approval, and the first takes its lane and slot back only when they are free; cancelling a parked run leaves both counters balanced (`tests/test_approval_parking.py`). An admin save that omits `max_concurrent` or the approval keys keeps them (`tests/test_control_persistence.py`). A scheduled run's due time is skipped while the previous run is active; failed, cancelled and interrupted runs count toward the pause; `last_run.state` is the real outcome (`tests/test_scheduler.py`); unattended approvals and gates are denied at once (`tests/test_unattended_approvals.py`); Stop holds queued follow-ups until run or discarded (`tests/test_followup_hold.py`).

## Migration

- **State**: only `install.sh` moves it, after its preflight (decision D24); a server start (`keepharness`, `python -m control`, boot, the desktop client) with the default `--state` refuses while the old folder waits, and `approve-device` and `--scan` never move it. Stop any running Tail Harness admin first: while it runs (active `tail-harness.service`, an old port that answers, a process with files open in the old folder, or a Python inside it) nothing moves, also when both folders already exist; the message names the pid and command that hold the port. A systemd unit or script that passes `--state ~/.local/share/tail-harness` explicitly keeps working in place; reinstall to move it. Moving the state moves a virtual environment kept inside it (`install.sh` layout); `install.sh` rebuilds it and reinstalls the package.
- **Both folders exist** (for example after an earlier pre-release start split them): `install.sh` moves nothing, unless the new folder holds only a client MCP bridge, which is set aside so the old state can move (acceptance criterion 2), and logs a warning naming both folders. `./install.sh --merge-legacy` prints a merge plan and changes nothing; `--apply` refuses while either folder is in use, when both hold a conversation database or when one conversation's sessions or uploads exist in both, then writes a 0600 tar backup of both folders (environments excluded) to `~/.local/share/keepharness-merge-<stamp>.tar`, copies `jobs.sqlite3` and `approval_sessions.sqlite3` with SQLite's online backup (integrity and job counts checked, never overwriting), copies everything else `tail-harness/` lacks, keeps `tail-harness/`'s settings, keys and `runtime.json`, appends the audit logs, marks `runs/` as Tail Harness state and renames `keepharness/` to `keepharness.split-<stamp>`. The merged folder opens in 0.14.0; `./install.sh` then moves it.
- **Rollback to 0.14.0**: `./install.sh --rollback-to-0.14` refuses when `~/.local/share/tail-harness` already exists (it never nests or merges), disables and removes `keepharness.service`, its launcher and menu entry, waits until no process uses the state, deletes the 0.15 environment (`venv/`), renames `runs/harness-agents` to `runs/tail-agents`, resets a KeepHarness identity marker to the Tail Harness value, moves the state and config folders back with `runtime.json` rewritten, and writes `~/.local/share/tail-harness.rolled-back`. While that record exists nothing moves to KeepHarness again; delete it and run `./install.sh` to upgrade again. Agents selected in conversations started on 0.15.0 (`harness/agents/<id>`) are unknown to 0.14.0.
- **MCP bridge on this computer**: a bridge that `setup-mcp.sh` installed on the harness host lives in `~/.local/share/tail-harness`, so it moves with the folder and its registered command stops working. Run the new `setup-mcp.sh` again (it installs into `~/.local/share/keepharness-mcp`) and remove the old server with `claude mcp remove tail-harness`. A bridge a pre-release `setup-mcp.sh` put in `~/.local/share/keepharness` is set aside by the state migration (see "Both folders exist"); re-run the installer once, and delete the `keepharness.bridge-*` folder when you no longer need it.
- **Native sessions**: the first turn of an existing "No project" Claude or Gemini conversation after the move starts a fresh native session from the harness history (see acceptance criterion 8); later turns resume that new session.
- **Run folders**: provider run folders now live in `~/.local/share/keepharness-sessions`. The old ones under `~/.local/share/keepharness/runs/sessions` are left in place and no longer used: the next turn of every existing conversation starts a new native thread from the harness history. Remove the old folder once you no longer need it.
- **Rotate the vpn key after upgrading**: earlier Read only runs could read `vpn.key`. Stop KeepHarness, delete `~/.local/share/keepharness/vpn.key` and the `clients.vpn` entry of `~/.local/share/keepharness/runtime.json` (the admin reuses that entry's hash otherwise), start it again, then give the new key to each MCP bridge computer. The vpn key is a guest: it can no longer pick Automatic or Full access.
- **Environment variables**: rename every `TAIL_HARNESS_<NAME>` you set to `KEEPHARNESS_<NAME>` (for example `KEEPHARNESS_AGENT_URL`, `KEEPHARNESS_LIVE`, `KEEPHARNESS_PYTHON`). The legacy unprefixed aliases (`LOCAL_AGENT_URL`, `LOCAL_AGENT_CLIENT`, `LOCAL_AGENT_CONFIG`, `TH_VENV`) are still accepted with a deprecation warning.
- **MCP on another computer**: run the new `setup-mcp.sh` there; it installs into `~/.local/share/keepharness-mcp` and registers the `keepharness` server. Move `~/.config/tail-harness/client.json` to `~/.config/keepharness/client.json` on that computer, then remove the old server with `claude mcp remove tail-harness`. An old bridge keeps working until it is removed.
- **Browser**: the onboarding tour key is `keepharness-tour-seen` and the tour becomes eligible again with the new version.
- **Developers**: the repository is `sophia-phillipa/keepharness`; project agents use the context stem `keepharness` (rename local `.codex/agents/*_tail-harness_*.toml` files and their `name` fields); the project skill is `.agents/skills/test-gauntlet_keepharness_procedure`.
- No database migration. Persisted `sem-projeto`, Tailscale identifiers and the internal Codex provider ids `tail_api` and `tail_local` (recorded in existing Codex threads) are unchanged.

- Pre-merge review fixes (backend): full pytest **3025 passed, 27 skipped**, against a baseline of 3001 passed and 27 skipped on `8eafcd2`, with the same two environment tests deselected.
