# 0.15.0 — KeepHarness: Space pages, scheduled tasks and a desktop client

## Behavior

The product is renamed from Tail Harness to **KeepHarness**, and the chat gains the Codex desktop's Space and Scheduled concepts, a detail view for each connector and plugin, and an Electron client.

- **Rename**: the product name, package and console scripts (`keepharness`, `keepharness-install`, `keepharness-mcp`, `keepharness-local`), the MCP server name, the icon, the systemd unit and launcher, the environment variables (`KEEPHARNESS_*`), the state folder (`~/.local/share/keepharness`), the client config folder (`~/.config/keepharness`), the shared UI package (`harness_ui`, browser globals `HarnessUI` and `HarnessTheme`) and the repository (`https://github.com/sophia-phillipa/keepharness`) all use the new name. The old `TAIL_HARNESS_*` variables are not read any more; the admin logs one warning per such variable still set when it starts, naming its `KEEPHARNESS_*` replacement.
- **Harness agents** (formerly "Tail agents"): the API is `/v1/harness-agents`, resource ids are `harness/agents/<id>`, the scope and origin are `harness`, the folder is `harness-agents/` and the error codes are `harness_agent_*` (`harness_resources_unavailable` for an unselected `@@` marker). Calling an agent with `@@name` is unchanged.
- **Space › Pages**: private Markdown pages next to a project's conversations, with a title and body editor (Ctrl/⌘ S, preview with the chat's renderer), **Attach to message**, **Start chat with this page** and a two-step delete. API: `GET/POST /v1/pages`, `GET/PUT/DELETE /v1/pages/{id}`.
- **Scheduled tasks**: recurring prompts (daily, weekly or every N hours, in local time) with project, provider, model, effort and access (Ask or Read only). A background check every 30 s submits each due task once, as its owner, through the same path as `POST /v1/jobs`; it never catches up missed runs, pauses after three failures in a row and defers while the harness is busy (`queue_full`, `owner_queue_full`, `submission_rate_limit`); any other refusal, such as `job_storage_limit`, is a failure. A run replayed after a crash whose prompt was edited in between records the job it already submitted instead of failing on `idempotency_conflict`. Conversations started by a task carry a **Scheduled** label. API: `GET/POST /v1/schedules`, `PUT/DELETE /v1/schedules/{id}`, `POST /v1/schedules/{id}/run`.
- **Plugin detail**: each row of the Plugins panel opens what the connector or plugin is, whether this conversation may use it and why not, its install status, its use in this project and the approval note. Remote ChatGPT plugins are reported as not available in Codex and DeepSeek runs, which turn Codex apps off.
- **Approval enrollment**: a `403 approval_session_required` answer carries `owner`, the caller's own owner id, so the browser can show the exact `keepharness approve-device --owner <id>` command.
- **Desktop client** (`desktop/`, Electron 44.4.1): starts the local admin when it is not running, opens the harness (or the admin when no provider is ready) in a sandboxed window and sends other links to the system browser. `KEEPHARNESS_PYTHON`, `KEEPHARNESS_ADMIN_PORT` and `KEEPHARNESS_PORT` configure it. No packaged build yet.

## Acceptance criteria

1. No product-facing string, identifier, package, script, path or environment variable keeps the old name; `rg -i "tail[ _-]?harness|tail_ui|TailUI|TailTheme"` finds only release notes before 0.15.0 and the migration code, tests and comments that name the old paths on purpose. Tailscale names and the `sem-projeto` protocol id are unchanged.
2. When the server starts with the default state folder (and in `install.sh`), `~/.local/share/tail-harness` moves to `~/.local/share/keepharness` when the new folder does not exist and the old one is unmarked or marked as Tail Harness (or already adopted); its identity markers stay `{"slug":"tail-harness","lineage":"tail-harness"}` (an unmarked folder gets that marker), which KeepHarness opens as its own, and the absolute paths in `runtime.json` follow the move through an atomic write. `~/.config/tail-harness` moves to `~/.config/keepharness` under the same rule. The move holds a lock (`~/.local/share/tail-harness.migration.lock`, removed once nothing is left to move) and is refused while `tail-harness.service` is active, while a port named in the old `runtime.json` (`port`, `admin_url`) answers on 127.0.0.1, or while the running Python lives inside the old folder; a move the system refuses (`EXDEV`, `EBUSY`) is refused the same way, never a crash. A refused move prints why and asks to stop Tail Harness and run `./install.sh`; the server then exits non-zero before anything creates `~/.local/share/keepharness` (the desktop client shows that message), and `install.sh` stops. An existing new folder is never merged into: each start logs a warning naming both folders and how to recover. A folder of another identity is left alone, a fork never takes Tail Harness state, an explicit `--state` folder is used in place (nothing moved), and other subcommands (`approve-device`, `--scan`) never move anything; `approve-device` with the default state refuses while the old folder still waits to move.
3. `install.sh` stops the old `tail-harness.service` and moves the state before it creates the virtual environment, and stops if the move is refused; `install.sh --check-only` neither stops the service nor moves anything, and refuses while the old state still waits to move. A virtual environment that moved with the state folder is rebuilt (`venv --clear`), the old `tail-harness` distribution is uninstalled from it so its console scripts disappear, and the package is reinstalled; `keepharness-install` disables the old unit and removes its unit file, launcher and menu entry before installing the new ones.
4. At service startup the agents folder `tail-agents/` moves to `harness-agents/` when only the old one exists; a follow-up turn of a persona started before the upgrade (stored as `tail/agents/<id>`) keeps answering as `harness/agents/<id>`.
5. A settings bundle exported by Tail Harness (`format: "tail-harness-settings"`) still imports; any other foreign format is refused.
6. A theme chosen before the rename (`tail-harness:theme:*` in the browser) is kept on the first paint; the new key wins once it exists.
7. Provider processes still never inherit `TAIL_HARNESS_*` variables, and integrations may not declare them.
8. Claude Code and Gemini key their native sessions by working directory, so a "No project" conversation whose folder moved cannot be resumed. When `claude --resume` reports the session missing, or Gemini's `session/load` fails, the adapter sets the stored `claude-session.json` / `gemini-session.json` aside (`*.before-session-missing`) and the turn runs once more in a fresh native session seeded with the harness's own history, the same path as a provider switch. Nothing under `~/.claude/projects` or `~/.gemini` is renamed.
9. Space, Scheduled, plugin detail and the desktop navigation policy pass their own suites; the full Python and UI suites pass with coordinated version identifiers.

## Migration

- **State**: automatic when the `keepharness` server (or `python -m control`) starts with the default `--state`, and in `install.sh`; `approve-device` and `--scan` never move it. Stop any running Tail Harness admin first: while it runs (active `tail-harness.service`, an old port that answers, or a Python inside the old folder) nothing moves, and KeepHarness does not start; it prints why and asks you to stop Tail Harness and run `./install.sh`. A systemd unit or script that passes `--state ~/.local/share/tail-harness` explicitly keeps working in place; reinstall to move it. Moving the state moves a virtual environment kept inside it (`install.sh` layout); `install.sh` rebuilds it and reinstalls the package.
- **Both folders exist** (for example after an earlier pre-release start split them): nothing is merged or moved. KeepHarness uses `~/.local/share/keepharness` and logs a warning at each start naming both folders. To keep the older data instead, stop both services, move `~/.local/share/keepharness` aside and run `./install.sh` again; remove `~/.local/share/tail-harness` once you no longer need it.
- **Rollback to 0.14.0**: stop KeepHarness, move `~/.local/share/keepharness` back to `~/.local/share/tail-harness` (and `~/.config/keepharness` to `~/.config/tail-harness`) and reinstall 0.14.0. The identity markers keep the Tail Harness value, so 0.14.0 opens the state; folders that 0.15.0 created from scratch carry the KeepHarness marker and 0.14.0 refuses them. Rename `runs/harness-agents` back to `runs/tail-agents` to keep the harness agents; agents selected in conversations started on 0.15.0 (`harness/agents/<id>`) are unknown to 0.14.0.
- **MCP bridge on this computer**: a bridge that `setup-mcp.sh` installed on the harness host lives in `~/.local/share/tail-harness`, so it moves with the folder and its registered command stops working. Run the new `setup-mcp.sh` again and remove the old server with `claude mcp remove tail-harness`.
- **Native sessions**: the first turn of an existing "No project" Claude or Gemini conversation after the move starts a fresh native session from the harness history (see acceptance criterion 8); later turns resume that new session.
- **Environment variables**: rename every `TAIL_HARNESS_<NAME>` you set to `KEEPHARNESS_<NAME>` (for example `KEEPHARNESS_AGENT_URL`, `KEEPHARNESS_LIVE`, `KEEPHARNESS_PYTHON`). The legacy unprefixed aliases (`LOCAL_AGENT_URL`, `LOCAL_AGENT_CLIENT`, `LOCAL_AGENT_CONFIG`, `TH_VENV`) are still accepted with a deprecation warning.
- **MCP on another computer**: run the new `setup-mcp.sh` there; it installs into `~/.local/share/keepharness` and registers the `keepharness` server. Move `~/.config/tail-harness/client.json` to `~/.config/keepharness/client.json` on that computer, then remove the old server with `claude mcp remove tail-harness`. An old bridge keeps working until it is removed.
- **Browser**: the onboarding tour key is `keepharness-tour-seen` and the tour becomes eligible again with the new version.
- **Developers**: the repository is `sophia-phillipa/keepharness`; project agents use the context stem `keepharness` (rename local `.codex/agents/*_tail-harness_*.toml` files and their `name` fields); the project skill is `.agents/skills/test-gauntlet_keepharness_procedure`.
- No database migration. Persisted `sem-projeto`, Tailscale identifiers and the internal Codex provider ids `tail_api` and `tail_local` (recorded in existing Codex threads) are unchanged.
