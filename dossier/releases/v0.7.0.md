# Version 0.7.0 — provider deadlines and human approval authority

## Behavior

- Codex RPC and Claude native/scoped reads have a configurable 300-second idle deadline. Known active tools use a separate 3,600-second tool-idle deadline, so a silent tool can finish without an ordinary idle failure. Missing tool completion cannot disable the watchdog forever. Human approval callbacks run outside these read deadlines. Expiry reports `provider_idle_timeout`.
- Provider stderr is continuously drained into a 64 KiB tail. Environment secrets, credential fields, authorization headers and cookies are redacted before a `provider_stderr` event or terminal `error_detail` is persisted. Process groups are terminated and pipes drained on cancellation, failure and completion. Gemini diagnostic pipes and provider subprocess environments use the same boundary.
- Job results distinguish `active_seconds`, `elapsed_seconds` and `human_wait_seconds`; existing queue and total timing fields remain. Pending human approval pauses active runtime and tool-idle, never wall-clock elapsed time. Default active limits remain 600 seconds for bounded jobs (including scoped Codex), 3,600 seconds for Maestro and no fixed active limit for native Codex.
- Human waits expire after 1,800 seconds, deny the request and persist `approval_expired`. The UI retains an **Approval expired** card, disables its actions and gives recovery guidance. Keyboard focus and expired status survive delayed HTTP responses.
- Provider capacity is acquired inside `ConversationService.infer`, including Maestro planning and steps. Capacity is released on success, failure or cancellation and honors changed limits. Cancellation follows per-job task ownership and cleans up execution descendants. Internal `execution_parent_id` is distinct from conversation `parent_job_id`; execution children of a running parent are eligible, while follow-up conversation turns remain serialized. Public submissions cannot forge execution ancestry. The singleton queue remains; this release adds no concurrent lanes.

## Human approval authority

Approval resolution requires an opaque, approval-capable `harness_session` cookie issued by device enrollment. Cookies are HttpOnly and SameSite=Strict, with Secure on HTTPS. Enrollment nonces are single-use, expire in ten minutes and are stored as hashes in `approval_sessions.sqlite3` in the configured harness state directory. Sessions also use hashed storage and expire after thirty days. Existing permissive enrollment files are repaired to private permissions.

API bearer tokens, ordinary login cookies, bare localhost requests and Tailscale headers do not confer approval authority. The login route cannot upgrade a token. MCP approval resolution is denied for every lineage; a human session can approve any job belonging to its existing owner, including a different job lineage. Owner/project authorization is still checked. Provider children do not inherit harness tokens, cookies or administrative secrets; explicitly configured provider authentication is retained.

**Isolation is advisory wherever a worker has unrestricted shell access as the same operating-system user.** Such a worker can read secrets accessible to that user, invoke the owner CLI or alter private state. Cookie flags, environment filtering and private file modes do not provide a separate-user security boundary. Enforced isolation requires state and enrollment credentials outside worker-readable paths; this release does not introduce an effect executor, a credential vault or stronger operating-system isolation.

## Migration and device enrollment

No owner identifiers, conversation history, `sem-projeto`, `tailscale_logins` or `tailnet-<hash>` identifiers are renamed. Existing API access continues, but an existing browser must enroll before resolving approvals. Existing configured approval policies and remembered rules retain their established scope.

From the owner's server terminal, with the **existing control state directory**:

```sh
tail-harness --state /path/to/control-state approve-device --owner local
tail-harness --state /path/to/control-state approve-device --owner tailnet-EXISTING_HASH
```

A configured tailnet login is accepted instead of its owner id. The owner is mandatory; unknown owners are rejected rather than creating a replacement identity. The CLI reads `runtime.json`, uses its configured browser origin and prints a link. Open that link in the intended browser within ten minutes and confirm **Enable approvals on this browser**. Merely opening the link does not consume it. Use the same command to enroll another browser or replace an expired session. Keep enrollment links private. An already-enrolled admin-panel enrollment flow and session-management UI are not included.

Install the updated package and refresh browser assets through the normal owner-managed upgrade process. This work did not start, enable or restart any system service.

## Configuration

These are JSON runtime configuration keys, not new environment-variable contracts. Owner-managed configurations can set them; this release does not add admin-panel controls or persistence through regeneration by the control panel.

| Location | Key | Default | Meaning |
|---|---|---|---|
| Provider configuration (`codex`, `claude`, and Codex-backed adapters) | `idle_timeout_seconds` | 300 | Ordinary blocked read deadline |
| Same provider configuration | `tool_idle_timeout_seconds` | 3600 | Blocked read deadline while a tool is active |
| Runtime root | `approval_timeout_seconds` | 1800 | Independent human-wait expiry |
| Runtime root | `active_timeout_seconds` | 600 / 3600 | Override for bounded non-native-Codex jobs / Maestro |
| `services.<provider>` | `max_concurrent` | 1 | Inference dispatch capacity, without adding queue lanes |

Idle settings that are invalid, nonfinite or nonpositive fall back to defaults. Invalid active/approval deadlines fail closed; invalid active settings cannot start an orphan process. Capacity must be a positive integer. Elapsed time keeps advancing during human waits and is included in job results; no new elapsed-time ceiling is introduced.

## Acceptance criteria and regression evidence

| Contract | Evidence |
|---|---|
| Silent reads stop, active tools get their own deadline, approval waits do not consume idle time | `tests/test_adapter_idle_watchdog.py` |
| Flooded stderr cannot deadlock; tails stay bounded and redact split/truncated credentials and Basic/Digest/Bearer headers | `tests/test_adapter_stderr_capture.py` |
| A simulated human wait exceeding ten minutes survives; real queue pause/resume, cancellation and active deadlines work | `tests/test_budgets.py` |
| Expiry denies, persists one expiry event and cannot be resolved by a late request body | `tests/test_approval_timeout.py`, `tests/test_approval_authority.py` |
| Planner/step dispatch, capacity changes, cancellation descendants and conversation order hold | `tests/test_dispatch_capacity.py`, `tests/test_composer_queue.py` |
| Worker HTTP/MCP/token/localhost attempts fail; enrolled migrated local and tailnet owners approve across their lineages | `tests/test_approval_authority.py` |
| Visible expiry, replay, narrow layout, repeated clicks and keyboard focus recover | `tests/harness-approval-expiry.spec.cjs` |

The browser fixture simulates seven distinct profiles; it is not a study with real users:

| Profile | Executed scenario |
|---|---|
| Beginner | Expired label and resend guidance |
| Rushed user | Double decision submits once; expired HTTP response disables retry |
| Domain professional | Reopening and replay keep one expired card |
| Keyboard user | Expiry restores focus, including during submission and a late HTTP error |
| Mobile user | Narrow viewport, reload and replay preserve disabled expired state |
| Harness engineer | Missing human authority has device-enrollment guidance |
| UI/UX specialist | Consistent title, readable status and no browser exceptions |

Independent review found and closed orphan execution on invalid timeout, stale capacity after reconfiguration, cancelled children left running, permissive enrollment files, Basic/Digest stderr leakage, unread-stdout teardown blocking, and approval-expiry races. Authors and reviewers were distinct.

## Actual validation

No cloud inference, live provider account, GPU benchmark, personal credential test or production service operation is part of this release's evidence.

- Initial Python baseline: **1,131 passed, 3 failed, 18 skipped, 12 subtests passed**. Two failures came from the runner setting `CODEX_HOME` over fixtures that select their own temporary homes; corrected runs remove provider-specific home overrides. The remaining failure assumed the checkout folder was named `tail-harness`; its test now copies the actual sprite into a temporary canonical project folder. Product icon discovery was unchanged.
- Initial UI baseline: **88/88 spec files passed**.
- Final Python: **1,183 passed, 18 skipped, 12 subtests passed** in 46.96 seconds (`.venv/bin/python -m pytest -q`). The 103 warnings are existing Starlette deprecations. The first integration run found an old assertion requiring a rejected backend to remain an active executor; its expectation now matches dispatch-only registration. The complete suite passed after that correction and the delayed-approval regression.
- Final complete UI invocation: **87 passed / 2 failed out of 89 spec files** (`PYTHON="$PWD/.venv/bin/python" ./scripts/test-ui.sh`, with the local Playwright module/cache configured). `h13-phone-novice` and `h29-model-explorer` timed out during `page.goto` before their scenario interactions. Both then passed in an isolated **2/2** rerun, with unchanged code and thresholds. The new approval-expiry spec passed all **eight scenarios across seven simulated profiles** in both complete runs. Every UI file passed against the final implementation, but **a single completely green full UI invocation after these changes was not obtained**; release-wide UI sign-off remains qualified by these intermittent navigation failures.
- An intermediate UI run passed 86/89 files: `harness-files-panel` timed out while uploading twenty files, `h26-long-session` exceeded its 200 ms input threshold, and `h40-chaos-monkey` timed out during navigation. All three passed when rerun in isolation with unchanged code, assertions and thresholds; the final complete rerun is reported above.
- Conventions: **0 name errors, 0 name warnings, 0 Portuguese hits**, including README heading parity (`.venv/bin/python scripts/check_conventions.py`). Ruff passes for the changed Python code and tests; `git diff --check` is clean. Runtime/package version identifiers and the installed editable distribution report **0.7.0**.

Tests use temporary home/config/data directories and synthetic provider subprocesses. Python 3.12 initially lacked `ensurepip`; the already-installed `uv` seeded pip into the requested `.venv`, followed by `.venv/bin/python -m pip install -e '.[test]'`. Playwright was installed under the ignored `.venv/ui-tools` directory and used the installed Chromium cache. The Maestro pilot window was already closed; token/cost savings were not measured or claimed.
