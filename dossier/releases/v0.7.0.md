# Version 0.7.0 — provider deadlines and human approval authority

## Behavior

- Codex RPC and Claude native/scoped reads have a configurable 300-second idle deadline. Known active tools use a separate 3,600-second tool-idle deadline, so a silent tool can finish without an ordinary idle failure. Missing tool completion cannot disable the watchdog forever. Human approval callbacks run outside these read deadlines. Expiry reports `provider_idle_timeout`.
- Provider stderr is continuously drained into a 64 KiB tail. Environment secret values of at least eight characters, credential fields (including `nonce`), authorization headers and cookies are redacted before a `provider_stderr` event or terminal `error_detail` is persisted. Short values are still redacted in named secret fields, without replacing common fragments throughout diagnostic text. Process groups are terminated and pipes drained on cancellation, failure and completion. Gemini diagnostic pipes and provider subprocess environments use the same boundary.
- Job results distinguish `active_seconds`, `elapsed_seconds` and `human_wait_seconds`; existing queue and total timing fields remain. Pending human approval pauses active runtime and tool-idle, never wall-clock elapsed time. Default active limits remain 600 seconds for bounded jobs (including scoped Codex), 3,600 seconds for Maestro and no fixed active limit for native Codex.
- Human waits expire after 1,800 seconds, deny the request and persist `approval_expired`. The UI retains an **Approval expired** card, disables its actions and gives recovery guidance. Keyboard focus and expired status survive delayed HTTP responses. Two consecutive expirations cancel the job with `approval_expiration_limit`; the UI preserves the cancellation reason and retry guidance even if no answer was streamed; a human, automatic or remembered decision resets the counter. The threshold is configurable.
- Provider capacity is acquired inside `ConversationService.infer`, including Maestro planning and steps. Capacity is released on success, failure or cancellation and honors changed limits. Cancellation follows per-job task ownership. Unused execution-ancestry traversal and descendant cancellation have been removed because no production phase creates execution children. Each job pauses its own budget during human waits; follow-up conversation turns remain serialized. Ancestry is deferred until a phase actually creates child jobs. The singleton queue remains; this release adds no concurrent lanes.

## Human approval authority

Approval resolution requires an opaque, approval-capable `harness_session` cookie issued by device enrollment. Cookies are HttpOnly and SameSite=Strict, with Secure derived from the configured browser URL as well as the request scheme, including HTTPS terminated by a reverse proxy. Enrollment nonces are single-use, expire in ten minutes and are stored as hashes in `approval_sessions.sqlite3` in the configured harness state directory. Sessions also use hashed storage and expire after thirty days. Session-store schema initialization and private-permission repair run at service startup and CLI operations. Authentication performs a single read-only session lookup after throttling; it does not run DDL or permission repair. Permission repair uses no-follow file descriptors and tolerates unsupported or unsafe targets. It no longer runs during authentication; regression tests cover a symlinked SQLite journal without modifying its target.

API bearer tokens, ordinary login cookies, bare localhost requests and Tailscale headers do not confer approval authority. The login route cannot upgrade a token. MCP approval resolution returns a tool error (`isError`) for every lineage; a human session can approve any job belonging to its existing owner, including a different job lineage. Owner/project authorization is still checked. Provider children do not inherit harness tokens, cookies or administrative secrets; explicitly configured provider authentication is retained.

**Isolation is advisory wherever a worker has unrestricted shell access as the same operating-system user.** Such a worker can read secrets accessible to that user, invoke the owner CLI or alter private state. Cookie flags, environment filtering and private file modes do not provide a separate-user security boundary. Enforced isolation requires state and enrollment credentials outside worker-readable paths; this release does not introduce an effect executor, a credential vault or stronger operating-system isolation.

Cookies are not isolated by port. Do not run untrusted services on other ports of the same host used for approval sessions; HttpOnly and SameSite do not create that boundary. See [RFC 6265 section 8.5](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5).

## Known limitation and planned follow-up

**S3 — owner decision, 2026-09-30:** holders of an API/MCP token can submit jobs selecting `access_mode` `full` or `auto` and execute without a human approval when the existing policy permits it. Human-only approval resolution does not restrict selection of these pre-existing execution modes. This release deliberately leaves the submit behavior unchanged. A follow-up will define and enforce who may select modes that bypass a human wait, while preserving existing owner identities and project grants.

## Migration and device enrollment

No owner identifiers, conversation history, `sem-projeto`, `tailscale_logins` or `tailnet-<hash>` identifiers are renamed. Existing API access continues, but an existing browser must enroll before resolving approvals. The schema upgrade resets **all pre-0.7.0 remembered approval rules once**, because workers could have created them without human authorization. Users must re-approve those actions. Rules remembered after this migration survive restarts; configured approval policies retain their established scope.

From the owner's server terminal, with the **existing control state directory**:

```sh
tail-harness --state /path/to/control-state approve-device --owner local
tail-harness --state /path/to/control-state approve-device --owner tailnet-EXISTING_HASH
```

A configured tailnet login is accepted instead of its owner id. The owner is mandatory; unknown owners are rejected rather than creating a replacement identity. Enrollment requires interactive TTY confirmation before creating a nonce; explicit `--yes` permits automation. The CLI reads `runtime.json`, uses its configured browser origin and prints a link. Open that link in the intended browser within ten minutes and confirm **Enable approvals on this browser**. Merely opening the link does not consume it. Use the same command to enroll another browser or replace an expired session. Keep enrollment links private. An already-enrolled admin-panel enrollment flow and session-management UI are not included.

Revoke approval sessions and pending enrollment links from the owner terminal:

```sh
tail-harness --state /path/to/control-state approve-device --revoke --owner local
tail-harness --state /path/to/control-state approve-device --revoke --all
```

`POST /v1/logout` revokes the current browser session in the session store and expires its cookie. Revocation takes effect on the next request and does not delete owners or history.

Install the updated package and refresh browser assets through the normal owner-managed upgrade process. This work did not start, enable or restart any system service.

## Configuration

These are JSON runtime configuration keys, not new environment-variable contracts. Owner-managed configurations can set them; this release does not add admin-panel controls or persistence through regeneration by the control panel.

| Location | Key | Default | Meaning |
|---|---|---|---|
| Provider configuration (`codex`, `claude`, and Codex-backed adapters) | `idle_timeout_seconds` | 300 | Ordinary blocked read deadline |
| Same provider configuration | `tool_idle_timeout_seconds` | 3600 | Blocked read deadline while a tool is active |
| Runtime root | `approval_timeout_seconds` | 1800 | Independent human-wait expiry |
| Runtime root | `approval_max_consecutive_expirations` | 2 | Cancel after this many consecutive expired human waits |
| Runtime root | `active_timeout_seconds` | 600 / 3600 | Override for bounded non-native-Codex jobs / Maestro |
| `services.<provider>` | `max_concurrent` | 1 | Inference dispatch capacity, without adding queue lanes |

Idle settings that are invalid, nonfinite or nonpositive fall back to defaults. Invalid active/approval deadlines fail closed; invalid active settings cannot start an orphan process. Capacity must be a positive integer. Elapsed time keeps advancing during human waits and is included in job results; no new elapsed-time ceiling is introduced.

The browser fixture simulates seven distinct profiles; it is not a study with real users:

| Profile | Executed scenario |
|---|---|
| Beginner | Expired label and resend guidance |
| Rushed user | Double decision submits once; expired HTTP response disables retry |
| Domain professional | Reopening and replay keep one expired card |
| Keyboard user | Expiry restores focus, including during submission and a late HTTP error |
| Mobile user | Narrow viewport, reload and replay preserve disabled expired state |
| Harness engineer | Missing human authority has device-enrollment guidance; repeated expiry cancellation keeps its explanation and recovery text |
| UI/UX specialist | Consistent title, readable status and no browser exceptions |

Authors and reviewers were distinct. The pre-merge security follow-up additionally reviewed session revocation, startup-only initialization, single-lookup authorization, enrollment consent, legacy rule reset, stderr redaction and removal of unused ancestry machinery.
