# DeepSeek's own CLI and harness: research note (issue #33, D-038)

Researched 2026-10-07. Read-only web research plus three slices of this repo. Nothing was installed, executed or logged in. Every factual claim carries a source URL or the mark **UNVERIFIED**. Web pages were read through a summarising fetch tool, so exact strings should be re-checked against the linked source before they go into code or a spec.

Short answer: Sophia's recollection is right. DeepSeek publishes an official, open-source (MIT) agent harness, **DeepSeek Harness (`dsh`)**, whose tagline is "Everything is a Plugin". ## 4. Run protocol for automation

`dsh` has several launch profiles; each is a different process contract. Source: https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/apps/cli/README.md

| Command | Contract |
| --- | --- |
| `dsh --profile headless "job"` | "Run single persisted session, output answer, exit" |
| `dsh --profile acp` | "Serve automation clients over ACP stdio" (Agent Client Protocol) |
| `dsh --profile sdk` / `sdk-minimal` | JSON-RPC over stdio for SDK clients |
| `dsh web` | Web UI |

Launcher flags are only `--profile <name>`, `--from-default-profile <name>`, repeatable `--patch <path>`, `--dump-config`, `--dump-config-schema`, `--dump-default-config`, `-V/--version`; `dsh <name>` expands to `dsh --profile <name>`; everything after the first unrecognised token goes to the app. Source: https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/apps/cli/src/args.ts

### Headless

- Documented contract: a one-shot task creates one fresh persisted agent, waits for quiescence, flushes the session, prints the last non-empty assistant text to stdout, streams reasoning to stderr under a `dsh: reasoning:` heading, "exits 0 for `completed`, else 1". It mounts no HTTP server or browser. Source: https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/apps/cli/reference/README.md
- The v0.1.7-rc.1 release notes add: tasks from stdin, session continuation with `--session-id`, and newline-delimited JSON run events with `--json`. Source: https://api.github.com/repos/deepseek-ai/deepseek-harness/releases/tags/dsh-v0.1.7-rc.1 . The reference README (read at `master`) does not mention `--json` or `--session-id`, and the launcher parser does not own them, so the documents disagree or are out of date. Treat as UNVERIFIED until a spike confirms the current flags with `dsh --profile headless --help` (not run here).
- UNVERIFIED: the JSON event schema (event names, tool-call, approval, token usage fields), exit codes in `--json` mode, how model and provider are chosen in a headless run, and whether stdout under `--json` is clean of reasoning text.
- Approvals and sandbox in headless: the approval policy `never` rejects every ask deterministically ("the strict headless stance (CI, unattended runs)"): https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/subsystems/approval.md . Permission presets: `workspace-write`, `danger-full-access`, `auto` (auto-review, current session only) and a derived `custom`; each bundles a sandbox mode and an approval policy: https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/subsystems/permission-presets.md . Sandbox modes `read-only`, `workspace-write`, `danger-full-access`: https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/subsystems/sandbox.md . The command-line way to pick a preset in headless is UNVERIFIED (docs say "applications call `set(session, name)`").
- Inference (not stated in the sources): the headless profile documents no channel for answering approval requests live, so it cannot reproduce KH's interactive approvals; that is the case for the ACP profile below.

### ACP (best fit for KH)

- The ACP package "provides a server that lets programs and automation run persistent DeepSeek Harness agents over the standard Agent Client Protocol": create, list, resume and close sessions, attach standard MCP servers, select model options, send text and image prompts, receive semantic updates, answer permission prompts, cancel work. JSON-RPC over stdio. Source: https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/acp/README.md . ACP protocol version used: UNVERIFIED.
- KH already speaks ACP for Gemini (`adapters/gemini/native.py`: `initialize`, `session/load`, `run_acp`), so a DeepSeek-via-`dsh` adapter could reuse that transport. Source: this repo, `adapters/gemini/native.py`.
- The ACP bridge is "automation-only" and exposes "fresh harness agents": whether `dsh --profile acp` can resume a session created by an interactive `dsh web` session is UNVERIFIED.
- SDK profile: a Python package `deepseek_harness` (`DeepSeekHarness(provider="deepseek-official", model="deepseek-v4-flash", ... profile="sdk-minimal")`, `harness.run(prompt, session_id=...)`) launches `dsh --profile sdk-minimal` and talks JSON-RPC on stdio. `sdk-minimal` "pins `danger-full-access`", so it is not a sandboxed route. Source: https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/user/guide/python-sdk.md . The PyPI name and version of that Python package: UNVERIFIED (not looked up).

## 8. Fit with KeepHarness

### Current path (a): Codex engine over DeepSeek's Responses API

From `adapters/deepseek/backend.py`: KH launches Codex `app-server` with per-process `-c` overrides: `model_provider="tail_api"`, `base_url` from the provider config, `wire_api="responses"`, `requires_openai_auth=false`, `env_key` set to a KH-named variable holding the key read from KH's private key file (`deepseek.key`, mode 0600, `adapters/deepseek/account.py`), websockets off, reasoning summary `none`. ### What a DeepSeek-via-`dsh` adapter needs from the provider-adapter seam

The provider-facade design (`dossier/provider-facade-design.md`) did not exist yet when this note was written, so these are requirements on the seam, not a reading of it. Today's contract is `run_native(config, prompt, event, project, model, effort, session_dir, approve)` in `adapters/__init__.py` and `adapters/README.md`.

1. Engine selection separate from provider identity: "DeepSeek via Codex" and "DeepSeek via DeepSeek Harness" must coexist during migration, with a visible engine name (`adapters/README.md` "Model x engine").
2. A transport abstraction that is not Codex-specific: a JSON-RPC-over-stdio ACP client (reuse the Gemini one), with explicit mapping of ACP updates to KH `event` calls and ACP permission prompts to `approve`.
3. A per-provider state home resolver: `DSH_HOME` (default `~/.dsh`) and `DSH_AGENTS_HOME` (default `~/.agents`), with fake homes for tests (project rule: tests never touch the owner's real homes).
4. A per-provider state reader/writer for each extension kind with its own format: skills (shared `.agents/skills`, plus `.dsh/skills`), instruction files (`$DSH_HOME/AGENTS.md`), MCP and plugins (YAML patch `insert` entries), hooks (`hooks.json` consumed by a bridge plugin). Writes must be atomic and patch-layer aware; external-change detection (D-038 follow-up) should watch `$DSH_HOME/cordis.patch.yml`, `profiles/*/cordis.patch.yml` and the skill roots.
5. Login/credential operations by CLI-owned means: either `dsh`'s account login or the API key in `$DSH_HOME/.credentials.yaml`; the seam needs a "provider login status" and "log in / renew" action per provider that is not hard-wired to a KH key file. Format and commands: UNVERIFIED, spike required.
6. Run policy mapping: KH permissions to `workspace-write` / `danger-full-access` presets and approval policy (`never` for scheduled and guest runs); no use of `sdk-minimal` for untrusted work because it pins `danger-full-access`.
7. Session identity: store the `dsh` session id in KH's native marker (as `native-thread.json` does for Codex), plus the adapter spec revision; resume through ACP `session/load` or equivalent, if `dsh` supports it for persisted sessions (UNVERIFIED).
8. Orchestration/hook gating for guests and scheduled runs: because `dsh` can run Claude/Codex hooks and third-party plugins in-process, KH must control which plugins and hook bridges are mounted per run (`--patch` overlays per run are the documented mechanism).
9. Capability and version probe: `dsh --version` and `--dump-config` at startup, a `compatibility.json` per the existing spec convention, and a hard failure on unsupported versions (given the breaking-change warning).
10. Usage and quota: keep the `/user/balance` panel; add token usage from `dsh` only once its event schema is confirmed.

### Recommendation

Move to `dsh`, but staged, and not yet as the default: it is the official DeepSeek harness and the only candidate with a standard automation protocol (ACP) and the "plugin everything" model Sophia remembered, so it is the right long-term engine for D-038's autonomy goal. It is a developer preview with announced compatibility breaks and an under-documented headless contract, so keep the Codex route as the supported default until a spike proves the ACP run loop (events, approvals, resume, token usage) and `dsh` has at least a non-prerelease tag. Ship `dsh` first as an opt-in "DeepSeek via DeepSeek Harness" engine behind the provider seam, pin the tested version, and decide on switching the default after the gates in issue 33.6. This is a recommendation for Sophia's decision, not a change of D-038.
